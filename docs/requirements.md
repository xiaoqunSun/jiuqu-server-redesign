# 产品需求与待确认事项

本文区分已确认方向与从旧服务端推测的需求。旧代码提供线索，不自动成为新产品要求。

## 已确认方向

- 新服务端按重新理解后的产品需求设计，不按旧服务器结构迁移。
- 现阶段唯一必须保持的客户端约束是协议兼容；协议以后可以通过明确版本计划替换。
- 新项目与旧仓库隔离。
- 首期持久化使用 MySQL；不要求 accessToken 一定存在，缺失或发送空令牌的客户端必须保留兼容登录路径。

## 当前需求假设

从旧服务端可见的功能推测，产品需要支持：

- 客户端建立实时连接并加入课堂/协作房间。
- 房间成员、教师或管理员等不同权限角色。
- 房间变量、事件、白板页面与样式、投票、聊天和在线状态。
- 主房间与子房间/分组房间之间的协作。
- 断线重连、活动记录与回放。
- 排课资料中的课程结束时间及 K12 房间自动下课。

这些功能仍需由产品目标确认，不能仅因旧代码存在就视为必须保留。

## 设计前需要量化

- 同时在线连接数、单房间峰值人数、单房间消息峰值。
- 可接受的端到端延迟与服务可用性目标。
- 哪些状态必须跨进程重启保留；允许的数据丢失窗口（RPO）和恢复时间（RTO）。
- 房间结束后聊天、白板、投票和回放的保留时间。
- 是否要求跨区域部署、跨房间共享状态或离线编辑。
- accessToken 存在时由哪个系统签发、用户与角色如何权威解析；无 token legacy 路径如何限制暴露面。

## 暂定数据分类

- 临时数据：心跳、实时光标位置和短时在线状态；实时光标可合并、过期或丢弃。为兼容旧回放，服务端另每 250 毫秒按身份采样持久化最新光标位置。
- 房间业务状态：成员关系、变量、白板、投票；逐项定义保存与恢复语义。
- 历史数据：聊天记录、回放；定义持久化边界、查询方式和保留周期。
